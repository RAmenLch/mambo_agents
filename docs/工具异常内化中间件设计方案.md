# 工具异常内化中间件设计方案

> 状态：**已实施**（v0.4.2b5）
> 目标仓库：`mambo_agents`
> 适用范围：**所有**通过 `ToolNode` 执行的工具调用（主图与子代理通用）
> 实现文件：`middleware/tool_call_error.py`、`utils/cancellation.py`
> 测试文件：`tests/test_tool_call_error_middleware.py`

---

## 1. 定位

`ToolCallErrorMiddleware` 是一个**工具调用钩子**，不进入图、不产出节点，只套在
“工具调用”这一层外面。它的职责只有一条：

> **工具执行期异常不得中止超步，必须以 `ToolMessage(status="error")` 的形式
> 成为该次工具调用的结果。**

它不处理“工具报错”（参数校验失败、工具不存在——`ToolNode` 自带处理），
也不处理 LLM 调用异常（那发生在 `model` 节点）。

---

## 2. 问题背景

### 2.1 默认行为

`ToolNode` 的默认错误处理是 `_default_handle_tool_errors`
（`langgraph/prebuilt/tool_node.py:382`）：

```python
def _default_handle_tool_errors(e: Exception) -> str:
    if isinstance(e, ToolInvocationError):
        return e.message
    raise e          # ← 工具执行期异常一律上抛
```

`create_agent` 不暴露 `handle_tool_errors` 参数（`langchain/agents/factory.py`
全文件无此关键字），因此无法通过配置调整。

仓库内已有一套同类机制：`BackendToolsMiddleware` 把 `BackendError`
转成 `status="error"` 的 `ToolMessage`（`middleware/backend_tools.py:761-808`）。
本中间件与它是**互补**关系：`BackendError` 仍在 `BackendToolsMiddleware` 内层被
拦截，本中间件负责其余运行期异常（超时、连接、限流、5xx、文件不存在……）。

### 2.2 一次异常中止整个超步的后果（已实测）

一个超步内并行调用 A（成功）、B（抛异常）时：

| 步骤 | 发生的事 |
|---|---|
| 1 | B 抛异常，`PregelRunner` 取消同超步其它任务并向上抛（同步路径经 `executor.map`，`tool_node.py:820`） |
| 2 | `after_tick()` 不执行 → 该超步的写入**未合并进 channel** |
| 3 | A 的 `ToolMessage` 只存在于 pending writes，`channel_values` 中没有它 |
| 4 | 后续无论走“带新输入”还是“父图 fork”，A 的结果都会丢失 |
| 5 | 悬空调用修补会给 A 也补一条 “was cancelled” → 模型误以为 A 没做 → **重做已成功的副作用** |
| 6 | 若未装悬空修补，则留下孤立 `tool_call` → 严格校验的 OpenAI 兼容接口返回 400 |

实测证据（`InMemorySaver` + 并行 `ok_tool`/`boom_tool`）：

```text
无中间件：invoke 抛 RuntimeError；checkpoint 只剩 [AIMessage]     ← c1 结果丢失
有中间件：checkpoint = [AIMessage, ToolMessage(c1), ToolMessage(c2, error)]
```

### 2.3 为什么必须在工具层解决

异常一旦离开 `ToolNode`，超步的中止就已经发生，后续任何补偿都只能是“事后拼凑”。
只有在工具返回的那一刻就把异常变成 `ToolMessage`，超步才不会被打断。

## 3. 机制

### 3.1 在调用链上的位置

```text
LangGraph 执行 tools 节点（ToolNode）
    └── ToolNode._run_one(tool_call)
          └── wrap_tool_call 链          ← 中间件插在这里
                └── execute(request)
                      └── _execute_tool_sync()
                            └── tool.invoke(...)    ← 异常从这里冒出
```

`create_agent` 把所有中间件的 `wrap_tool_call` 串成一条链
（`factory.py:885-904` → `_chain_tool_call_wrappers`，**列表第一个 = 最外层**）。
中间件要做的就是在 `handler(request)` 外面包一层 `try/except`。

### 3.2 核心实现

```python
def wrap_tool_call(self, request, handler):
    if not self.enabled:
        return handler(request)
    try:
        result = handler(request)
    except GraphBubbleUp:            # 控制流，必须冒泡
        raise
    except _PROGRAMMING_ERRORS:      # 代码缺陷，必须冒泡
        raise
    except Exception as exc:         # 其余运行期异常
        if is_cancellation_related(exc):
            raise                    # 取消/停止生成，必须冒泡
        return self._internalize(request, exc)   # 内化
    self._clear_streak(request)      # 成功后清零连续失败计数
    return result
```

`awrap_tool_call` 只把 `handler(request)` 换成 `await handler(request)`，
其余逻辑与 `_internalize` 完全共用。

`except` 顺序是**语义要求**，不是风格问题：

1. `GraphBubbleUp` 必须最先 → 见 §4.2；
2. `_PROGRAMMING_ERRORS` 必须在内化之前 → 见 §4.1；
3. 取消判定必须在 `_internalize` 之前 → 见 §4.4。

### 3.3 返回值

`_internalize` 返回一个 `ToolMessage` 而不是继续抛出：

```python
ToolMessage(
    content=f"Tool '{name}' failed: {type(exc).__name__}: {exc}"[:2000],
    name=name,
    tool_call_id=call_id,
    status="error",
    additional_kwargs={"tool_error": {
        "tool_name": name,
        "error_type": type(exc).__name__,
        "message": detail[:1000],
        "retryable": bool,
        "streak": int,
        "escalated": bool,
    }},
)
```

`ToolNode` 收到 `ToolMessage` 后按正常结果处理 → 该超步正常合并提交 →
并行兄弟工具的结果得以保留。

| 字段 | 作用 |
|---|---|
| `tool_call_id` | 必须与 `AIMessage.tool_calls` 的 id 对应，否则成为孤立 `tool` 消息，严格校验的接口返回 400 |
| `name` | 工具名，前端展示与调试定位 |
| `status="error"` | 让上层区分“正常结果”与“失败结果” |
| `content` / `message` | `content` 进入模型上下文（截断 2000），`message` 供告警/展示（截断 1000） |

`_internalize` **内部不得抛异常**：`tool_call_id` 缺失时退化为 `""`（
`ToolMessage.tool_call_id` 必须是 `str`，`None` 会触发 pydantic `ValidationError`，
在 except 处理器里抛出会直接打断超步）。

## 4. 捕获边界

### 4.1 分类规则

| 类别 | 处理 | 原因 |
|---|---|---|
| `GraphBubbleUp`（`GraphInterrupt`、`ParentCommand`、`NodeInterrupt`） | **上抛** | 中断是控制流而非错误，必须冒泡让图暂停等人决策 |
| `asyncio.CancelledError`、`KeyboardInterrupt`、`SystemExit`、`GeneratorExit` | **自然上抛** | 非 `Exception`，`except Exception` 天然抓不到 |
| 取消信号被包装成普通异常 | **上抛** | 见 §4.4（实测：判据是 `task.cancelling()`，不是异常类型） |
| 编程错误：`TypeError` / `AttributeError` / `NameError` / `AssertionError` / `NotImplementedError` / `ImportError` | **上抛** | 代码缺陷，内化会掩盖问题并诱导模型在坏代码上反复重试 |
| 框架状态错误：`InvalidUpdateError` / `EmptyInputError` | **上抛** | 状态 schema / 图装配写错，同属代码缺陷 |
| 业务/环境类：超时、连接错误、断流、限流、4xx/5xx、文件不存在、权限不足、外部服务错误 | **内化为 `ToolMessage`** | 运行期可预期失败，模型可据此换策略 |
| 其它未识别 `Exception` | **内化**（保守），计入连续失败计数 | 保证超步不被打断 |

`GraphRecursionError`（继承 `RecursionError`，**不是** `GraphBubbleUp`）按“其它”
处理：内化后模型看到“子图递归超限”，可换策略，比打断整个超步更好。

### 4.2 为什么必须显式放行 `GraphBubbleUp`

继承链为 `GraphInterrupt → GraphBubbleUp → Exception`
（`langgraph/errors.py:80/84/111`），即 **`GraphInterrupt` 是 `Exception` 的子类**。

若只写 `except Exception`，工具内部的 `interrupt()`（如 `ask_user`、
人工审核中间件）会被当成“工具失败”吞掉，主图永远收不到 `__interrupt__`，
人机审核整体失效。

实测：`GraphInterrupt` / `ParentCommand` / `NodeInterrupt` 三种均原样上抛。

> 测试注意：验证 interrupt 穿透必须用**带 checkpointer** 的编译图，
> 否则 Pregel 会在无 checkpoint 的情况下静默结束，基线也会“不抛异常”，
> 测试会假通过。

### 4.3 可重试性判定

```python
_RETRYABLE_STATUS = {408, 409, 425, 429, 500, 502, 503, 504}
_NON_RETRYABLE_STATUS = {400, 401, 403, 404, 405, 406, 410, 413, 415, 422}

def _is_retryable(exc) -> bool:
    code = _status_code(exc)                      # 沿异常链找 status_code / response.status_code
    if code is not None:
        if code in _NON_RETRYABLE_STATUS:
            return False
        return code in _RETRYABLE_STATUS or 500 <= code < 600
    names = " ".join(type(n).__name__ for n in iter_exception_chain(exc))
    if any(h in names for h in _NON_RETRYABLE_NAME_HINTS):
        return False
    return any(h in names for h in _RETRYABLE_NAME_HINTS)
```

要点：

- **按数值判断状态码**，不做字符串子串匹配。反例（旧方案会踩）：
  `httpx.HTTPStatusError` 因类名不含提示词被判 `retryable=False`，
  而语义等价的 `openai.RateLimitError` 被判 `True`。
- 判定沿**整条异常链**进行，`APITimeoutError → httpx.ReadTimeout` 这类包装
  也能匹配到 `Timeout`。
- 未知异常默认 `retryable=False`：不鼓励盲目重试。

结论写入 `additional_kwargs["tool_error"]["retryable"]`，供模型判断
“换参数重试”还是“换策略”，也供子代理的熔断逻辑复用。

### 4.4 取消信号识别

#### 4.4.1 为什么需要

`except Exception` 天然抓不到 `CancelledError`，但**取消信号要穿过工具、HTTP 客户端、
序列化层才到中间件**。任何一层把它转成普通异常，中间件就会把它当成“工具失败”内化掉。
一旦被内化，后果是：超步正常提交 → 模型被再次调用 →
**用户点了停止，后端仍把这一轮跑完**。

#### 4.4.2 实现（`utils/cancellation.py`）

只依赖标准库，两个判据：

```python
def is_cancellation_related(exc: BaseException) -> bool:
    # 主判据：当前 task 是否处于 cancelling
    if _task_is_cancelling():
        return True

    # 辅助判据：异常链
    saw_cancellation = saw_timeout = False
    for node in iter_exception_chain(exc):
        if isinstance(node, TimeoutError):
            saw_timeout = True
        elif isinstance(node, (asyncio.CancelledError, GeneratorExit)):
            saw_cancellation = True
    return saw_cancellation and not saw_timeout
```

`iter_exception_chain` 同时沿 `__cause__`、`__context__` 与
`ExceptionGroup.exceptions` 展开，带节点上限与环检测。

#### 4.4.3 判据优先级与实测依据（关键）

**主判据必须是 `Task.cancelling()`，不是异常链。** 这一点在实施阶段用真实 HTTP 调用
实测确认过，先前“上下文链是确定性、不可伪造的主判据”的判断是**错的**：

```text
httpx.ReadTimeout
 └─ httpcore.ReadTimeout
     └─ builtins.TimeoutError
         └─ asyncio.CancelledError(Cancelled via cancel scope ...; reason: deadline exc)
```

`httpcore` 的异步后端用 `anyio.fail_after()` 实现超时（`httpcore/_backends/anyio.py:33`），
机制就是“取消当前 task + 转 `TimeoutError`”，因此**每一次 HTTP/SDK 超时的上下文链里
都必然有 `CancelledError`**。若以异常链为主判据：

| 实测用例 | 只按异常链判定 | 实际语义 |
|---|---|---|
| `httpx.ReadTimeout` | 判为取消 → 上抛 | 超时，应当内化 |
| `openai.APITimeoutError` | 判为取消 → 上抛 | 超时，应当内化 |
| `anyio.fail_after` 裸 `TimeoutError` | 判为取消 → 上抛 | 超时，应当内化 |

即“超时”这一头号内化目标会 100% 失效，超步照样被打断。
而同一批用例中 `current_task.cancelling() == 0`；真正被用户取消时（`task.cancel()`）
该值为 `> 0`，且 anyio 在 cancel scope 退出时会 `uncancel()`
（`anyio/_backends/_asyncio.py:489-492`），deadline 型取消不会残留。

因此最终规则：

| 情形 | 判定 |
|---|---|
| `task.cancelling() > 0` | **取消**（上抛）——能覆盖“工具吞掉 `CancelledError` 后再抛别的异常” |
| 链上有 `CancelledError` 但**同时有** `TimeoutError` | **超时**（内化）——anyio/httpcore 走的就是这条 |
| 链上只有 `CancelledError`（`raise X from CancelledError`） | **取消**（上抛） |
| 无事件循环（同步路径） | 退化为只看异常链 |

#### 4.4.4 三条注意

| 注意点 | 说明 |
|---|---|
| `cancelling()` 只能在**工具自己的 task** 里读 | 异步 `ToolNode` 用 `asyncio.gather` 并发调用（`tool_node.py:857`），`awrap_tool_call` 运行在每工具独立的 Task 中，`current_task()` 即该 Task。若在父 task 里 catch 异常再判定，会读到 `0` |
| 同步路径必须能安全退化 | `wrap_tool_call` 中没有运行中的事件循环，`asyncio.current_task()` 抛 `RuntimeError`，内部 `except` 兜住并退化为异常链判定 |
| `concurrent.futures.CancelledError` / `asyncio.TimeoutError` 无需单独处理 | Python 3.8+ / 3.11+ 起它们分别是 `asyncio.CancelledError` / `TimeoutError` 的别名 |

## 5. 连续失败升级

全部内化会导致真实失败被彻底掩盖：模型只看到一串 error `ToolMessage`，
用户侧完全无法感知。因此需要一道“别全吞了”的护栏。

### 5.1 语义（与初版方案的区别）

**达到阈值不再 `raise`**，而是提升可见性：

| 行为 | 说明 |
|---|---|
| 计数 | 进程内 `dict[thread_id, int]`，仅当 `config.configurable.thread_id` 存在时计数（缺失则**不计数**，避免把无关会话混成一个桶） |
| 清零 | 任意一次成功工具调用后清零 |
| 超阈值（`> max_consecutive_failures`，默认 3） | 日志级别 `WARNING → ERROR`（附 `exc_info`），并在 `additional_kwargs["tool_error"]` 中置 `escalated=True`、`streak=n` |
| 内存 | 表超过 `max_tracked_threads`（默认 1024）整体清空 |

`raise` 会重新制造 §2.2 的问题（整个超步丢失、兄弟结果作废）——实测确认：
共享实例下第 4 次可预期失败直接上抛，超步被打断。既然本中间件的唯一职责是
“不让工具异常中止超步”，就不应该在内部再制造一次中止；需要“硬失败”的场景
应交给应用层依据 `escalated` 标志或日志决定，而不是吞在中间件里。

### 5.2 跨进程计数（未实施）

需要跨副本共享时，可返回 `Command(update={"tool_fail_streak": n, "messages": [...]})`
把计数写进图状态。当前不实施：并行多工具时更新顺序不确定，需额外定义合并语义。

## 6. 挂载位置

### 6.1 主图（`graph.py`）

```python
mw: list[AgentMiddleware] = [
    BackendToolsMiddleware(...),   # 最外层：包装工具描述、大结果驱逐
    ToolCallErrorMiddleware(),     # ← 在此
    SkillsMiddleware(...), ...,
    PatchToolCallsMiddleware(),
    ReorderToolMessagesMiddleware(),
]
```

**位置是“`BackendToolsMiddleware` 之后”，即位于其内层**，而非链首。理由：

| 放链首（最外层） | 放 `BackendToolsMiddleware` 内层（已采纳） |
|---|---|
| 能兜住 `BackendTools` 自己抛的异常 | 兜不住，但那些异常是**事后处理**失败 |
| ❗ 工具**已成功执行**、事后处理（大结果驱逐）失败时，成功结果被替换成 error `ToolMessage` → 模型重做已产生副作用的操作 | 事后处理失败照常上抛，成功结果的语义不被篡改 —— 这正是 §2.2 第 5 条要防的 |

安全审核、版本备份、Skills/Memory 等中间件都在内层，其异常仍会被内化。
`PatchToolCallsMiddleware` / `ReorderToolMessagesMiddleware` 只实现 `before_agent` /
`before_model`，不入 `wrap_tool_call` 链（已核实），位置对本中间件无影响。

### 6.2 子代理（`middleware/subagents.py`、`middleware/async_subagents.py`）

子代理通过 `_langchain_create_agent()` 创建自己的 `ToolNode`，主图的中间件覆盖不到，
必须在子代理装配处挂载。挂在**子代理 middleware 列表的链首**：

```python
middleware = [ToolCallErrorMiddleware(), *spec.middleware]
if spec.interrupt_on:
    middleware.append(HumanInTheLoopMiddleware(interrupt_on=spec.interrupt_on))
```

- 子代理默认栈里没有 `BackendToolsMiddleware`（不做大结果驱逐），因此没有
  §6.1 那个“事后处理”顾虑，放链首可以连带兜住用户自定义中间件抛的异常；
- 子代理的 `interrupt_on` 由 `HumanInTheLoopMiddleware` 经 `GraphBubbleUp` 传播，
  本中间件放行，互不影响；
- `AsyncSubAgentMiddleware` 的子代理构造走同一模式，一并挂载。

> 注：初版方案写“子代理侧顺序为 `ToolCallError → PatchToolCalls → Reorder`”，
> 与代码不符——子代理栈中**根本没有**这两个中间件。已更正。

## 7. 边界与已知限制

| 限制 | 说明 | 缓解 |
|---|---|---|
| 改变工具异常的呈现方式 | 业务异常以 error `ToolMessage` 返回，不再上抛到应用层 | `enabled` 开关；`additional_kwargs["tool_error"]` + `WARNING/ERROR` 日志（含 `exc_info`）供下游展示与告警 |
| 进程内计数不跨进程 | 多副本部署时每个进程独立计数 | 需要时切换 §5.2 的状态计数方案 |
| `thread_id` 缺失时不计数 | 无法归属到具体会话 | 主图/子代理调用链都会带 `thread_id`，正常情况下不触发 |
| 不覆盖 LLM 调用异常 | 发生在 `model` 节点，与工具层无关 | 由子代理 `catch_errors` 与主图重试策略处理 |
| 不覆盖参数校验失败 | `ToolNode` 默认已处理 | 无需干预 |
| 不覆盖“工具成功后的后处理失败” | 见 §6.1 取舍 | 需要时把本中间件外移，但会带来成功结果被丢弃的风险 |
| `content` 进入模型上下文 | `str(exc)` 可能含 URL/路径等内部信息 | 截断至 2000；确需脱敏应在工具侧或展示层处理 |
| 同步/异步需分别实现 | 只实现一侧会在另一条链上抛 `NotImplementedError`（`factory.py:909-925` 用 `m.awrap_tool_call`，基类未实现则报错） | 两版共用 `_internalize` / `_is_retryable` |
| 依赖 asyncio 运行时语义 | 取消识别依赖 `asyncio` | 仅标准库；同步路径退化为异常链判断（§4.4.4） |
| 异常组被压平 | `ExceptionGroup` 会被内化成一条消息 | `BaseExceptionGroup` 含非 `Exception` 成员时不被 `except Exception` 捕获，仍会正常上抛 |

## 8. 模块清单（已实施）

### 8.1 `src/mambo_agents/middleware/tool_call_error.py`

- `ToolCallErrorMiddleware(AgentMiddleware)`
  - `__init__(*, enabled=True, max_consecutive_failures=3, max_tracked_threads=1024)`

## 9. 附：实施阶段的关键实测记录

| 项 | 结论 |
|---|---|
| 并行 A 成功 + B 抛错，A 结果是否保住 | 无中间件：checkpoint 只剩 `AIMessage`；有中间件：`c1`/`c2` 都在 |
| `httpx.ReadTimeout` / `openai.APITimeoutError` | 链中必带 `CancelledError(reason: deadline exc)`，`cancelling()==0` → 必须靠 `cancelling()` 主判据才能判成“超时” |
| `openai.RateLimitError`（429） | 链干净、`retryable=True`、正常内化 |
| `openai.InternalServerError`（500） | 链干净、`retryable=True`、正常内化 |
| `httpx.HTTPStatusError`（429） | 旧判据给出 `retryable=False`（错），已改数值判断 |
| `GraphInterrupt` / `ParentCommand` / `NodeInterrupt` | 三种均原样上抛 |
| 用户停止生成（工具内 `await sleep`） | `CancelledError` 正确上抛，不内化 |
| 工具吞掉取消后再抛 `RuntimeError` | 经 `task.cancelling()` 识别为取消并上抛 |
| `InvalidUpdateError` / `EmptyInputError` / `GraphRecursionError` | 前两者非 `GraphBubbleUp` → 已并入编程错误名单；后者按“其它”内化 |
| `ToolMessage.tool_call_id=None` | pydantic `ValidationError`（在 except 处理器内抛出会打断超步）→ `_internalize` 已退化处理 |
| 连续失败第 4 次（旧方案 `raise`） | 超步被打断，兄弟结果丢失 → 已改为“只升级可见性” |
